# 조사에서 얻은 개발 방향

이 문서는 조사 결과의 활용 방향이다. 기존 설계를 교체하거나 라이브러리 도입을 승인한 설계 결정 기록은 아니다. DB·자료 검색 체계는 다른 세션 범위로 남긴다.

## 여섯 분야를 어떻게 함께 참고할 것인가

| 필요한 공용 기능 | 기존 CAE 근거에 보충할 것 | 이번 근거 묶음 | 가져올 수 없는 의미 |
|---|---|---|---|
| 메뉴·툴바·단축키·도킹 | 명령 공유·컨텍스트·충돌 처리, 레이아웃 수명, 아이콘 grid·DPI·focus | `shell-P01–12` | API 존재는 완성된 외관·접근성이나 문서 변경의 유효성 보장이 아님 |
| 트리·선택·속성·viewport | active와 selected, visible와 through, mixed/unchanged/edited, 겹친 대상 후보의 preview·확정·취소 | `selection-P01–14` | GIS layer/Blender object/시각화 pipeline을 solver entity·해석 활성 상태로 치환할 수 없음 |
| 다중 파트·저장 참조·Undo | 표시이름/내부키, 공유/복사/외부 링크, 변경 기록 참여, 저장 상태·dependency와 재계산 구별 | `document-P01–11` | CAD label·Name·subshape naming은 solver 번호·다중 DOF·재메시 집합 복원의 보장이 아님 |
| 수치·재료 곡선·표 | draft와 확정값, locale, 절대/차이 단위, 가져오기 preview, 표 열과 plot 연결 | `engineering-input-P01–11` | 자동 타입 추정·경고 허용·빈칸 0/NaN 정책은 solver 수치 입력 정책과 다름 |
| 대형 메시와 표시·품질 | connectivity와 tag/집합, 조건부 복사·버퍼 수명, 필터 뒤 원본 대응, metric별 지원 범위 | `mesh-data-P01–10` | 표시 dataset과 원본 FE 문서, cell 차수와 DOF, 색칠과 수리는 서로 다름 |
| 작업·취소·결과 채택 | progress·token·실제 종료, process tree, timeout/로그, 단일 파일 교체, 수명/late callback | `jobs-P01–10` | kill/취소 통지는 solver stop·문서 rollback·여러 산출물 채택의 원자성을 보장하지 않음 |

즉 상용 CAE에서 ‘어떤 사용자 작업을 제공해야 하는가’를 조사하고, 다른 프로그램에서 ‘상태를 어떻게 드러내고 조작하는가’를 비교하며, 기술문서·코드에서 ‘실제 구현 책임과 제약은 무엇인가’를 확인한다. 세 종류는 서로 보충하며 하나가 다른 둘의 검증을 대신하지 않는다.

## 실제로 유용한 보완과 반례

겹친 객체 후보를 다루는 Rhino의 절차와 QGIS의 다중 편집 상태는 기존 CAE GUI 자료에서 남았던 선택·편집 동작을 더 구체적으로 설명한다. LabPlot의 가져오기 미리보기는 파일명/형식 선택뿐 아니라 열 타입과 실제 입력 행을 함께 확인하는 예다. 각각 다른 프로그램·mode·버전의 근거이며 하나의 완성된 CAE 흐름으로 합성하지 않는다.

문서·메시 분야에서는 보장 범위를 좁히는 근거가 특히 중요했다. 객체 이름의 재사용, 조건부 저장 반환, Undo 기록 참여, topology naming의 전제, 원본 ID 배열의 후속 연산 영향, 조건부 배열 복사, 미정의 품질값이 그 예다. 따라서 공용 자산의 외형뿐 아니라 현재 지원 범위·실패 상태·수치 의미를 함께 명세하는 데 활용해야 한다.

## 이번 외부 근거만으로 확인하지 못한 교차 상태

| 교차 경계 | 확인한 부분 | 외부 근거의 공백 |
|---|---|---|
| 여러 셀 paste → 문서 transaction | 편집 묶음·Undo API와 기존 프로그램의 입력 정책 | 한 셀이 invalid일 때 draft 보존/전체 거부/일부 적용, 중간 실패의 실제 rollback |
| 선택/필터 → action → 속성 draft | 선택 종류·가시성·활성 컨텍스트를 구분하는 사례 | 편집 중 대상 삭제·숨김·busy 변경 뒤 현재 draft와 명령의 정확한 처리 |
| worker cancel → 결과 → 문서 | 요청/종료·산출물/문서 변경을 구분하는 API | 입력 개정·대상 재생성·문서 닫기 뒤 late result 거부와 원자적 채택 |
| CAD 변화 → mesh → 조건 참조 | CAD naming과 필터 provenance의 조건부 지원 | 재메시 뒤 명시 집합·하중·접촉의 매핑과 모호성 해소 |
| 표시 단위 → 표/plot → native 출력 | 차원 검사·온도 차이·축 표시·원본 값의 구별 | solver별 필드 의미·허용 단위계·정밀도·재열기 검증 |
| 문서 객체 → 대량 배열 → lazy UI | 고수준 객체와 균질 배열, 증분 UI의 별도 책임 | 실제 편집/Undo/저장/worker의 동시 메모리와 선택 지연 |

이 표는 이번 외부 수집물의 공백이며 기존 설계 결정을 미결정으로 되돌리지 않는다. 이미 정한 입력 검증·stale 거부·후보 채택 계약은 유지한다. 조사 문서가 없는 동작을 구현·검증 완료로 처리하지 않으며, 실제 확인은 기존 `execution-stages.md`의 해당 단계와 종료 조건을 따른다.

## 기존 작업서와의 연결

P1의 계약 분리에는 셸/문서/선택 경계를, P2–P5의 자산·갤러리에는 메뉴·도킹·입력·곡선 상태를, P6의 다중 파트/데이터에는 문서 정체성·배열·참조 한계를 참고한다. P7의 CAD/메시 채택에는 recipe·품질·원본 대응을, P8의 작업/API에는 취소·수명·host 소유권을 참고한다. 이 연결은 참고 위치이며 기존 단계의 완료 기준을 변경하거나 미실증 메셔 기능을 확정하지 않는다.

Workbench는 기존 위젯 소비·독립 Prep 실행·파일/실행 관리 경계를 유지한다. 여러 제품의 프레임워크를 전부 제품 의존성으로 추가하지 않는다. 특정 모듈을 실제 재사용하려면 해당 버전의 바인딩·배포·라이선스·동작을 그 단계에서 확인해야 한다. API/소스가 공개됐다는 사실을 상용 기능의 구현 난이도가 사라졌다는 근거로 사용하지 않는다.
