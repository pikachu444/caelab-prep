# 공용 CAE 자산·기반 실행 계획

2026-11-12 재료 연구·자문·후처리 후속은 [기존 실행 단계의 연결 절](execution-stages.md#research-integration)에 편입했습니다. 현재 진도는 기존 CURRENT_STATE N표, 새 12개 세부 작업은 WB 기존 계획 아래에서 관리합니다. 단계·잔여·진행률을 별도로 더하지 않습니다. 원래 G1–G4·8제품·대용량·메셔·Windows 목표는 유지합니다.

원계획 기준일: 2026-10-29. 목표 정렬·구현 대조: 2026-11-02. 현재 반영 코드와 미완료 범위는 [CURRENT_STATE](../CURRENT_STATE.md)를 따른다. 상태: **구현된 기반과 남은 설계·작업 계획**. 달성할 제품 목표·동일 과업 T1–T6·단계 G0–G4의 완료 기준은 [DESIGN의 「달성 목표와 제품 완료 기준 (2026-11-02)」](../DESIGN.md#delivery-goals)에 단일 정의한다. 이 문서의 목표 경로·계약·갤러리는 구현 완료 목록이 아니다. 현재 실행 코드와 파일 계약은 [ARCHITECTURE](../ARCHITECTURE.md), 실행 방법과 지원 범위는 [README](../README.md)를 따른다.

이 문서는 공용 자산의 설계와 기술 작업 P0–P9를 위 목표에 맞춰 연결한다. A/B/C는 기존 범위를 구별하는 기록이며, A의 완료 보고나 기존 리뷰를 현재 제품 목표의 완료로 전용하지 않는다. 현재 구현 근거는 [단계별 작업서 19절](../CURRENT_STATE.md#current-progress), 남은 작업의 번호·범위·완료 기준은 [중앙 잔여 목록](../CURRENT_STATE.md#remaining-work)에 둔다. 이 문서의 P 번호를 미완료 건수로 다시 합산하지 않는다. 19절의 존재는 앞의 1–18절이 완료됐다는 뜻이 아니다. Workbench 소비자와 두 저장소의 변경 책임은 [재사용 계획](workbench-reuse-plan.md)을 따른다.

메셔의 실제 재사용 코드·알고리즘/상용 매뉴얼 조사·SDK 실험과 착수 근거는 [실현 가능성 로드맵](mesher-feasibility-roadmap.md)에 둔다. 고급 중립면·hex/hybrid 항목은 이름을 적었다고 구현 가능한 것으로 선정한 것이 아니며, 기능별 실증 뒤 제품 연결 여부를 결정한다.

## 1. 목적과 이번 계획의 범위

CAELab Prep에 여러 공학 프로그램이 사용하는 공용 GUI 자산과 CAE 개발 기반을 축적한다. OpenRadioss/OpenCourant는 첫 적용 대상이고 현재 RAD 편집기는 첫 소비자다. 실행형 갤러리도 같은 공용 코드를 사용하는 정식 산출물이다.

2026-10-29에는 계획 문서만 작성했으며, 이후 공용 위젯·셸·provider/저장 계약과 G1–G4의 구현 묶음이 병합됐다. 현재는 RAD 객체 생성·할당, 곡선/집합/조건, tri/tet CAD 후보 채택과 Starter/Engine 출력, 실제 Workbench의 공용 숫자 입력·독립 문서 전달까지 연결돼 있다. 다음 변경은 이 기반을 다시 만드는 작업이 아니라 아래 계획과 중앙 잔여 목록의 부족분을 닫는 작업이다. 이번 갱신 자체는 문서만 변경하며 새 제품 기능이나 검증 결과를 추가하지 않는다.

목표는 다음 세 가지를 함께 확보하는 것이다.

1. **외관 자산:** 정보 밀도, 글자·아이콘·간격·상태 표현을 제어할 공통 규칙과 리소스.
2. **실행 가능한 공학용 부품:** 트리·속성·단위·벡터·표·곡선·선택·뷰포트·도킹을 실제 값과 연결하는 컴포넌트.
3. **공용 앱 기반:** 문서·명령·선택·저장·작업·자동화의 작은 계약과 구현. 솔버·CAD 규칙은 적용 모듈에 유지한다.

HyperMesh·PrePoMax·Naksha·Abaqus/CAE·COMSOL·midas NFX·MeshFree·BeidPrep 각각의 방식으로 같은 지원 과업을 수행하는 GUI와 재사용 가능한 공통 기반을 목표로 한다. 제품별 정보 구성·명령 그룹·작업 순서·편집/확정 상호작용을 구현하며, 모델·검증·명령·Undo·저장과 편집 부품은 공유한다. 모든 제품의 물리 모델·솔버를 전수 복제하거나 자체 CAD 커널을 개발하겠다는 약속은 아니다. 실제 Workbench의 위젯 소비와 파일 전달은 G4의 필수 확인이며, 독립 QWidget 시험이나 갤러리 실행만으로 대체하지 않는다.

## 3. 참조 화면과 디자인 결정

[7제품 상세 벤치마크](benchmarks/2026-10-30/README.md)의 메뉴·입력·결과·취소/저장 근거와 [공용 자산 요구](benchmarks/2026-10-30/common-assets.md), PrePoMax를 포함한 [현재 8방식의 출처·구현·한계 표](ui-reference-variants.md#source-to-implementation-map)를 출발점으로 사용한다. 자료 미확인을 구현자의 추정으로 채우거나 정적 그림을 실행 결과로 승격하지 않는다. 동일 과업의 시작 상태·조작·결과와 근거의 확인 수준은 G0에서 고정한다.

기존 [참조 제품 비교](gui-reference-matrix.md)는 관찰 자료이며, 일부 제품의 패턴을 골라 하나의 화면으로 합치면 8방식 목표를 달성한 것으로 보지 않는다. 각 제품의 근거와 미확인 부분을 구분하고, 미확인 상호작용은 확인 과제로 남긴다.

### 같은 과업을 수행하는 8가지 작업 방식

각 방식의 과업 범위와 합격 기준은 DESIGN의 T1–T6를 따른다. 배치·색·제품명만 바꾼 화면은 충분하지 않다. 같은 입력 모델에서 프로그램별 탐색·명령 진입·선택·편집·확정/취소의 흐름을 제공하고, 그 결과는 공통 모델과 명령으로 일관되게 반영한다. GUI를 제품마다 복제하는 대신 표현과 상호작용을 어댑터로 분리한다.

기존 두 프로필 계획은 이 목표로 대체한다. 첫 구현의 완료를 Abaqus 한 방식으로 제한하거나 COMSOL 및 나머지 방식을 선택적 후속 작업으로 미루지 않는다. G1부터 해당 단계의 동일 과업을 8방식에서 검증한다. 실제 원제품 접근이 없는 항목은 문서/영상 근거와 실제 실행 근거를 구분하고 비교 미완료를 명시한다.

### 외관 규칙의 구체화

| 자산 | 첫 구현에서 정의할 내용 | 확인할 장면 |
|---|---|---|
| 밀도·글꼴 | 본문/제목/표 숫자 글꼴, 행·입력·툴바 높이, 들여쓰기, 패딩, 그룹 간격 | 같은 화면 크기에서 긴 트리·여러 속성·표가 함께 있는 장면 |
| 상태·색 | 기본·hover·선택·포커스·비활성·입력 오류·경고, 선택/미선택 형상의 대비 | 키보드 포커스, 선택 행, 잘못된 숫자, 비활성 명령 |
| 아이콘 | 의미별 키, 벡터 원본, 트리/툴바/명령 그룹별 크기와 상태 | 작은 트리 아이콘과 도구 아이콘을 실제 표시 크기로 비교 |
| 패널·도킹 | 제목·구분선·로컬 도구, 접기/숨기기, 최소 크기, 배치 저장 | 창 축소, 도킹 이동, 메시지 접기, 프로필 전환·재시작 |

아이콘의 초기 묶음은 문서/이력, 형상/부품, 메시/요소, 재료/단면, 하중/구속, 접촉/집합, 보기/선택, 곡선/결과, 작업/상태다. 서로 다른 객체를 모두 같은 문서 아이콘으로 표시하지 않는다. 지원하지 않는 명령을 아이콘 수를 늘리기 위해 활성화하지 않는다. 외부 아이콘은 해당 리소스의 허용 조건을 확인하고 자체 CAE 도형과 일관되게 조정한다.

갤러리 카탈로그의 등록 정보에는 자산의 의미 키·용도·원본 경로·사용 부품/장면·구현 상태·출처/허용 조건을 둔다. 리소스와 실제 사용 코드를 함께 관리하며 이를 위한 별도 데이터베이스나 새 제작 도구부터 만들지 않는다.

압축형 공학 UI를 기본으로 설계하되 글자 크기·고배율 가독성을 보존한다. 최종 행 높이·패널 폭은 현재 CSS 값을 일괄 축소해서 결정하지 않는다. 먼저 참조 자료의 해상도·배율·주요 영역과 자체 실행 화면을 비교해 초기 토큰을 정한다. 현재 필수 비교 환경은 DESIGN의 Windows 1920×1080/100%, 3840×2160/200%와 축소 창 960×640을 따른다. 기존 2560×1440/150%는 보조 검사로 유지할 수 있으며 필수 환경을 대신하지 않는다. 이는 후속 확인 계획이며 아직 실행한 결과가 아니다.

## 5. 유지·확장할 공용 계약

아래 최소 계약은 현재 RAD와 중립 provider·공용 위젯에서 사용한다. 새 기능도 같은 경계에 연결하며 임의 솔버의 전체 물리를 기술하는 범용 스키마부터 만들지 않는다. 곡선 드래그는 PR #17의 N15에서 구현했으며, 아래 계약의 구현 범위와 남은 작업은 중앙 N 작업표를 따른다.

| 계약 | 전달할 정보/동작 | 소유 경계 |
|---|---|---|
| 문서 세션 | 문서 이름·ID·개정·dirty·가능 동작 조회, 변경 구독, Undo/Redo, 저장 요청 | 앱이 문서·수명 주기를 소유. RAD 파일/INCLUDE 해석은 RAD 구현 |
| 트리·속성 제공자 | 객체 참조, 표시 이름·부모·아이콘·상태, 속성의 그룹·종류·값·단위 문맥·허용값·읽기 전용·오류 | 솔버가 의미·규칙을 제공. 위젯은 내부 키를 라벨로 추측하지 않음 |
| 편집 명령 | 대상 참조·기대 개정·필드·값·단위 문맥, 성공 변경/검증 오류 반환 | 최종 검증·모델 변경·Undo는 세션/코어의 같은 경로 |
| 선택·표시 | 활성 객체 참조, 선택 엔티티 집합, 관련 형상 강조, 원본 ID와 표시 인덱스의 매핑 | 공용 서비스가 상태를 동기화. 재료→부품 등 의미 연결은 제공자가 계산. 렌더러는 후보 pick을 전달하고 승인된 선택을 강조 |

파일 작업은 공용 FileTask의 상태·오류·산출물과 세션 이벤트를 사용하고, CAD 후보는 worker의 실제 취소/실패와 문서 채택을 구분한다. 독립 API/CLI는 같은 모델 명령을 호출한다. PR #21에서 병합한 N19/N20은 같은 열린 GUI의 주 스레드 owner에 IPC를 연결하고 얇은 MCP adapter로 노출한다. 실제 공개 client 검사와 정확한 SHA의 CI는 중앙 N 작업표에서 구분한다.

Action 정의는 ID·표시 이름·아이콘·단축키·문맥·활성/체크 상태와 실행 연결을 가진다. 메뉴·툴바·명령 탭·우클릭은 같은 정의를 사용한다. 지원 여부는 앱의 가능 동작에서 정하고, 갤러리에서만 동작하는 도구를 RAD 기능으로 표시하지 않는다.

상세 계약을 정할 때 다음 조건을 명시한다.

- **편집 중 값:** 입력 초안은 확정 값과 분리한다. scalar는 유효한 값만 확정하고 잘못된 값은 이동/저장을 막아 해당 입력과 오류를 유지한다. Escape/취소로 초안을 명시적으로 폐기할 수 있고 닫기의 변경 폐기 동작도 유지한다. 벡터·표 붙여넣기는 전체 검증 후 한 명령으로 적용한다. N15에서 구현한 곡선 드래그는 미리보기 후 놓을 때 한 명령, Escape로 취소한다. 선택 전환·Undo·저장·닫기의 초안 처리에 같은 규칙을 적용한다. 다른 호출자가 문서를 바꾸면 현재 개정을 다시 확인하고 초안을 조용히 덮어쓰지 않는다.
- **단위:** 현재 RAD는 덱/카드 단위 문맥을 보존한다. 알 수 없는 단위를 SI로 추측하지 않는다. 확인된 입력 덱 단위의 탄성계수·밀도·길이·속도·힘/모멘트는 provider가 표시 단위로 환산하고 Apply에서 원 단위로 되돌린다. FUNCT 축과 미해석 카드의 물리량은 추정하지 않는다.
- **명령 단위:** 한 번의 벡터 입력·곡선 표 붙여넣기는 하나의 Undo 작업으로 처리하며 N15의 곡선 드래그에도 같은 규칙을 적용한다. 현재 PR #20의 다중 자원 후보 검증·단일 publish/Undo 계약을 재사용한다. N18의 첫 절대좌표 이동은 sparse overlay/codec으로 main에 연결됐다. 나머지 메시 연산의 미완료 범위와 현재 저장 계약은 [ARCHITECTURE](../ARCHITECTURE.md#문서와-명령)를 따른다. 전체 NODE 블록 복사로 대체하지 않는다.
- **곡선 의미:** `FUNCT`의 축을 무조건 응력–변형률로 표시하지 않는다. 실제 사용 관계·축 이름·단위가 확인되면 제공자가 전달하고, 미확인 자료는 일반 X/Y와 확인된 단위 문맥만 표시한다. 현재 RAD는 FUNCT 생성/삭제·행 편집·CSV와 실제 CLOAD 참조를 지원한다. N15는 두 host의 CSV/plot drag와 RAD/VTK 없는 중립 실행을 각각 검사해 PR #17에 병합했다. 중립 자료의 `Associated curve` 참조를 재료 구성법칙이나 하중 연결의 구현으로 보고하지 않는다.
- **객체 참조:** UI 행 번호·VTK 배열 인덱스를 정본 ID로 쓰지 않는다. 현재 정수 절점/요소 ID와 자원 참조를 호환한다. 현재 생성/삭제 명령은 카드 UUID와 native ID를 구분하고 Undo·저장·재열기에서 정체성을 유지한다. 새 provider도 이 정책과 source별 native namespace를 명시한다.
- **pick 유효성:** 활성 재료/조건 객체와 절점/요소 선택을 하나의 ID 목록으로 강제하지 않는다. pick은 문서와 투영 자원 개정을 포함하며, 문서 교체·재메시 이후의 오래된 pick은 거부한다. 관련 형상 표시를 지원하지 않는 객체에 임의 연결을 만들지 않는다.
- **저장:** 현재 RAD 컨테이너·이전 버전 읽기·손상 판정의 정본은 [작업 파일 계약](../ARCHITECTURE.md#작업-파일과-native-덱)이다. 공용층은 원자적 파일 교체·manifest/version·자원 payload 묶기와 실패/dirty 처리를 제공한다. RAD 원문·patch·INCLUDE 의미와 실제 codec은 적용 모듈이 소유한다. 갤러리 배치는 모델 파일과 별도로 저장한다.
- **곡선 파일:** CSV는 데이터 교환 형식이다. 단위·재료 속성·곡선 관계를 보존하는 작업 문서는 공용 컨테이너와 별도 재료/곡선 codec으로 저장한다. RAD 전용 `.caeprep` v1의 의미를 조용히 바꾸지 않는다. 작업 문서 payload에는 값·단위 문맥·축 메타데이터·재료/곡선 참조와 자체 버전을 포함한다.
- **작업:** 파일·메시 작업의 진행·취소 요청·실패·결과 파일을 공통 자료로 전달한다. UI는 완료되지 않은 작업을 성공으로 표시하지 않는다. 초기부터 세션별 변경 직렬화와 이벤트의 UI 스레드 전달을 유지하고, 백그라운드 결과는 대상 문서가 여전히 유효한지 확인한 뒤 채택한다. 저장 완료는 실제 저장한 상태를 기준점으로 삼고 이후의 변경을 저장된 것으로 표시하지 않는다. VTK/Qt 조작은 UI 스레드에서 수행하고 무거운 작업은 기존 worker 경계를 사용한다.
- **자동화:** GUI·스크립트·MCP는 같은 조회/명령 경로를 사용한다. 열린 GUI의 IPC와 얇은 MCP adapter는 PR #21의 N19/N20에서 구현·병합했다. 실제 Linux GUI·공개 client 검사와 Windows·자연어 LLM 사용의 미확인 범위를 구분한다.

## 6. 외부 자산의 채택 순서

현재 실행 기반인 Qt Widgets/PySide6·VTK·Gmsh는 유지한다. 새 의존성은 필요한 한 역할을 실제 장면에서 비교하고 채택한다. 예제 코드 복사와 독립 라이브러리 사용, 호스트 전체 확장은 구분한다.

| 후보 | 맡길 역할 | 계획상 결정 / 채택 조건 |
|---|---|---|
| Qt 모델/뷰·delegate·QDockWidget | 트리·표·속성 편집·기본 도킹 | 기본 경로. 제공자와 모델을 연결하고 편집/선택 상태 보존 확인 |
| Qt ADS + PySide6 바인딩 | 자동 숨김·복잡한 도킹 | 비교 후보. Windows wheel·Qt/Shiboken 조합·라이선스·배치 복원을 확인한 뒤 도킹 backend로 선택. 실패해도 기본 도킹으로 진행 |
| pyqtgraph | 실제 곡선 표시·곡선 편집의 그래프 부분 | 우선 비교 후보. 표 데이터/Undo를 라이브러리에 소유시키지 않고 공용 곡선 모델을 투영. ParameterTree 전체 도입은 공용 속성 계약과 충돌 여부를 별도 확인 |
| Pint | 명시된 물리량·단위 검사/변환 | 알려진 단위 장면에서 검증할 후보. RAD의 단위 누락이나 솔버 규칙을 대신 추정하지 않음 |
| superqt | 검색형 콤보·범위/수량 입력 중 필요한 위젯 | 실제 장면에서 표준 Qt보다 이득이 있는 부품만 채택 |
| QtAwesome 등 | 범용 문서/상태 아이콘 | 리소스별 허용 조건과 스타일 일치를 확인. CAE 전용 의미는 자체 벡터로 보완 |
| FEBioStudio·BARAM·SALOME·ParaView·SMTK | 실제 CAE 설계·기능 기반 비교 | 현재 앱을 통째로 포크하는 결정과 구분. 필요한 컴포넌트의 결합·라이선스·이식 비용을 확인한 뒤 제한적으로 재사용 |

현재 프로젝트는 Python 3.11 이상과 조건별 PySide6 범위를 지원한다. 조사 당시 pyqtgraph/Pint 개발 브랜치의 Python 요구는 3.12 이상이고, Qt ADS 바인딩 저장소의 `.pyside-version`은 6.12.0이었다. 이는 안정 릴리스 전체의 요구조건을 뜻하지 않는다. `latest`를 일괄 설치하지 않고 **호환되는 릴리스 조합**을 찾아 Windows·갤러리·기존 RAD 앱에서 확인한다. 기존 지원 범위 변경이 필요하면 이유와 호환 경로를 함께 문서화한다. 이 문서 갱신으로 의존성을 추가하지 않으며 현재 선언은 `pyproject.toml`을 따른다. QDockWidget·QPainter plot·명시 단위 변환이 현재 채택 경로이고, ADS/pyqtgraph/Pint의 도입 자체를 필수 잔여로 세지 않는다.

## 7. 갤러리 장면과 자료

갤러리는 두 층을 가진다. 부품 화면에서 상태와 입력을 확인하고, 조합 화면에서 정보 밀도·비례·작업 연계를 확인한다. 공용 패키지가 갤러리 자료나 tests를 실행 의존성으로 사용하지 않게 한다. 갤러리는 개발·회귀 확인용 소비자이며, 실제 입력을 사용한 G1–G4의 작업 완료 증거를 대체하지 않는다.

| 장면 | 자료와 기능 | 실제로 확인할 작업 |
|---|---|---|
| 부품 목록 | 아이콘·버튼·메뉴·트리·속성·단위/벡터·표·메시지의 상태 목록 | 긴 이름·한글·지수 표기·입력 오류·비활성·키보드 포커스 |
| 재료/곡선 편집 | 탄성 상수·단위·벡터와 두 종류 이상의 곡선 자료, 표·그래프 | 값 수정·붙여넣기·단위 표시·검증 오류·Undo·저장/재열기 |
| 8방식의 작업 조합 | 같은 문서·제공자·실제 다중 부품 입력을 프로그램별 명령 그룹·탐색·편집 흐름으로 표시 | 해당 단계의 동일 과업을 각 방식에서 수행. 전환 시 값·선택·이력·초안 보존과 배치 복원 |
| 첫 RAD 적용 | 실제 사용자 RAD와 현재 소형 보존 시험 입력 | 기존 지원 필드 편집→저장→새 세션 재열기→RAD export. 미지원 원문 보존 |

조합 장면에는 여러 계층, 긴 이름, 펼침/접힘, 여러 속성 그룹, 표와 곡선을 포함한다. 현재 8절점/2셸 자료는 빠른 기능 확인에 남기고 대표 외관 장면은 다중 부품 셸/솔리드 자료로 구성한다. 형상이 다른 두 자료와 실제 사용자 파일 로딩 경로를 사용해 특정 모델 이름·개수에 맞춘 화면을 피한다. 필요한 자료는 재배포 가능한 소형 파일 또는 생성기로 제공한다.

갤러리 샘플도 실제 편집 가능한 자원과 명령을 사용한다. 샘플 결과·계산하지 않은 장면은 그 용도를 표시하고 실제 솔버 계산 결과처럼 보고하지 않는다. 작동하지 않는 메뉴를 채워 정보 밀도를 꾸미지 않는다.

## 8. 현재 코드의 이행 순서

아래는 원계획의 책임 분리 작업표다. 이미 분리된 항목을 다시 구현하지 않으며, 실제 코드와 현재 목표 사이의 부족분만 다음 변경의 대상으로 삼는다.

| 원계획 당시 위치 | 첫 분리 작업 | 반드시 보존할 동작 |
|---|---|---|
| `theme.py` | 토큰·아이콘·스타일 생성 분리 | 기존 앱에서도 같은 리소스 사용. 실제 크기·배율·선택 상태 확인 |
| `_action`, 메뉴·툴바 | Action 자료와 실행 연결 분리 | 현재 단축키·Undo/Redo·활성 상태, 한 명령의 중복 실행 방지 |
| `_refresh_tree` | 제공자 + Qt 모델/뷰로 분리 | 현재처럼 전체 clear/expand를 반복하지 않고 펼침·스크롤·선택·검색 보존 |
| `_refresh_fields`·초안 메서드 | 속성 제공자와 공용 편집기로 분리 | 미완료 입력·포커스·커서·오류·개정 충돌과 저장 전 편집 처리 |
| `_before_replace`·파일 작업·`closeEvent` | 문서 컨트롤러와 작업 표시 분리 | dirty 문서의 저장/취소, 저장 실패 시 창 유지, 비동기 열기/저장 오류 처리 |
| `PrepSession` | 공용 계약을 구현하는 RAD 제공자·codec으로 역할 분리 | 기존 GUI/CLI 호출 호환, 원문/INCLUDE·단위·patch·저장/출력 계약 |
| `MeshViewport` | 공용 프레임과 VTK/RAD 투영 연결 분리 | 원본 ID 역매핑, 문서 개정, 승인된 선택만 강조, 렌더러 종료 |
| QSettings·도킹 복원 | 안정적인 dock ID와 앱/프로필/배치 버전 키 | 프로필 간 배치 덮어쓰기 방지, 유실된 배치의 기본값 복구 |

각 분리는 한 사용자 작업이 끝까지 동작하는 작은 변경으로 연결한다. 모든 이름을 먼저 바꾸거나, UI를 새로 만들고 나중에 세션을 붙이는 일괄 재작성은 하지 않는다. 기존 실행 경로를 새 부품의 첫 소비자로 유지한다.

## 9. 작업 단위와 선행 관계

P0–P9의 입력·산출물·필수 확인·종료 조건은 [단계별 실행 계획](execution-stages.md)이 정본이다. 이 문서에서는 공용 계약과 의존 관계를 설명하며 단계별 상태표를 복제하지 않는다.

P0의 근거 수집과 P1의 계약 초안은 병행할 수 있지만, 제품의 확인 순서는 G0→G1→G2→G3이며, G4의 실제 소비·API·Windows 배포는 완성된 기능부터 병행한다. 원제품 접근의 보류는 비교 미확인으로 남기며, 확정된 계약에 따른 G1 코어 구현 전체를 막지 않는다. P2/P3/P5의 표현·상호작용과 P6a의 실제 변경 명령을 G1에서 연결하고, P4와 조건/케이스를 G2, CAD 후보와 출력을 G3로 이어 간다. 기술 조사의 병행이 앞 단계의 미완료를 숨기는 이유가 되지 않는다. 실제 작업 상태는 [단계별 작업서 19절](../CURRENT_STATE.md#current-progress), 소비자별 책임은 [Workbench 재사용 계획](workbench-reuse-plan.md)에 둔다. 확인되지 않은 인력·작업량을 전제로 완료 날짜를 약속하지 않는다.

## 10. 현재 구현과 다음 납품의 구분

G1의 재료·shell/solid 단면 생성·복제·안전 삭제·할당, G2의 곡선·집합·조건, G3의 CAD 후보·native 채택·Starter/Engine 출력은 병합됐다. G4의 실제 Workbench W1/W2 소비도 병합됐다. 이 범위의 코드·파일·Linux 렌더/solver 근거는 작업서 19절에 연결하며, 원제품 비교·전체 사용자 연속 작업·Windows 납품을 자동 통과로 바꾸지 않는다.

케이스 정의/조건 배정(N01), 첫 독립 MSH 입력(N02), 두 host의 CSV/plot drag(N15)는 PR #17의 명시 지원 범위로 병합했다. 제품별 비교·연속 작업·Windows(N03–N14)는 미완료다. Workbench RAD 실행(N21)은 PR #55의 실제 두 입력·필수 CI 통과 후 병합했다. IPC/MCP(N19/N20)는 PR #21의 실제 GUI·공개 client 및 최종 CI를 통과해 병합했다. 혼합 관계(N16)는 명시 B1–B4/B6 범위로 PR #20에 병합했고 대용량(N17)·일반 메시 수정(N18)는 미완료이며, 선/준비면·중립면·quad·sweep·hybrid(N22–N26)는 기능별 실증을 선행하는 조건부 범위다. 정확한 입력·완료 조건은 [중앙 잔여 목록](../CURRENT_STATE.md#remaining-work)을 따른다.

기존 `.caeprep` v1의 원문/patch 보존 계약과 공용 저장 절차는 살린다. 새 객체·관계의 저장 지원은 필요한 provider/codec에서 명시적으로 구현·검증한다. 중립 재료/곡선 파일의 성공을 RAD 새 카드 생성이나 실제 사용 관계의 보존으로 대신하지 않는다. 모든 솔버 카드 전수 지원이나 자체 CAD 커널 개발은 이 목표에 포함하지 않는다.

과거 묶음 A의 A1–A8 조건과 당시 판정은 [구현 이력](history/implementation-history.md)에 있다. 현재 제품 목표는 DESIGN의 G1–G4를 따른다.

### 묶음 B/C와 종료 판단

묶음 B는 [다중 파트·자유도·데이터 설계](cae-model-data-design.md)의 B1–B6과 고정 규모 예산에 대한 기술 범위다. 해당 조건을 만족하면 검증한 커밋·입력·환경과 함께 그 범위의 완료를 보고한다. A/B/C 중 일부의 완료가 제품 목표 전체의 완료를 뜻하지 않으며, 이미 확인된 기능은 회귀 기준으로 유지한다.

첫 CAD/메시 묶음 C는 [단계별 작업서](execution-stages.md)의 생성·품질·원자적 채택·조건/단위·저장·실패/취소·고정 native 범위 조건을 모두 통과하면 완료다. 중립면·일반 hex·모든 형상 변경 복구는 다음 단계이며 C의 종료를 막지 않는다. C만으로 상용 전처리기 전체 또는 실무 메시 편집 전체가 완성됐다고 하지 않는다. Workbench의 위젯 소비·독립 Prep 파일 전달·RAD 실제 계산도 [별도 조건](workbench-reuse-plan.md)으로 닫는다.

단계별 산출물은 기능·자료·환경·미완료를 명시해 배포한다. 최종 제품 목표의 판단은 DESIGN의 완료 기준을 따른다. 검사 수·진행률 대시보드·별도의 거대한 증명 문서는 종료 판단을 대신하지 않는다.

## 11. 검토와 기록 방식

외관은 실제 실행 화면으로, 편집은 실제 값과 파일로 확인한다. 메뉴 존재·검사 개수·해시를 제품 품질의 대체 지표로 삼지 않는다.

1. 각 제품과 Prep에서 같은 과업·대응하는 객체·시작/결과 상태를 맞춘 뒤 전체 화면과 트리/속성/툴바를 비교한다. 해상도·배율·행 높이·정렬·아이콘·패널 비율·빈 영역·문자 잘림을 기록한다. 물성/단면 수치와 작업 상태를 맞추지 않은 화면, Results 화면과 편집 화면의 단순 병치는 동일 과업 검증이 아니다.
2. 해당 단계의 실제 생성·할당·편집 과업을 사용자 파일에서 끝까지 수행하고 오류·취소·Undo·저장·새 세션 재열기·native 결과를 확인한다. 기존 scalar 변경이나 fixture만 통과한 결과와 구분한다.
3. 창 축소·도킹 이동·프로필 전환·재시작 시 배치와 모델 값이 섞이지 않는지 확인한다. 입력 중 외부 변경·닫기/저장 실패도 확인한다.
4. Qt 모델/뷰, 단위/참조 검증, Undo 경계, 저장 보존처럼 회귀 위험이 있는 동작에 검사를 둔다. 토큰 숫자나 위젯 내부 구현을 그대로 반복하는 검사는 만들지 않는다.
5. Windows 실제 실행, Linux 개발 확인, headless 검사, 미확인을 구분한다. 기존 README 이미지는 실행 기록으로 남기며 대표 이미지는 실제 새 갤러리/앱이 만들어진 뒤 교체한다.

각 작업 PR에는 바뀐 공용 부품·실제 소비자·대상 커밋·입력·환경·수행한 조작·실제 결과와 남은 범위를 적는다. 검토자는 기능 정확성·UI 품질·실무 과업·원제품 비교·재사용을 구분해 판정한다. 원제품 실행이나 실제 Windows 확인을 못 했으면 해당 판정은 미확인으로 남긴다. 별도의 거대한 증명 문서나 새 승인 절차를 추가하지 않는다.

## 12. 선택된 기반과 미해결 경계

| 항목 | 처리할 작업과 판단 기준 |
|---|---|
| 이미 만든 공용 GUI 저장소의 정확한 위치·소유 자산 | P0에서 확인. 이 계획은 해당 저장소나 진행 중 갤러리의 실물을 확인했다고 주장하지 않음. 원본을 이 저장소에 축적하는 방향으로 중복·의존 관계 정리 |
| 도킹 backend·리본 부품 | QDockWidget와 공용 QAction을 사용한다. 교체가 필요한 구체 문제 없이 backend 재선정부터 시작하지 않으며 Windows 동작은 N12/N13 |
| pyqtgraph/Pint 등의 채택 릴리스 | 현재 QPainter와 provider의 명시 변환을 사용한다. N15 등 실제 부족한 기능에 도입이 필요할 때만 호환 조합·배포 조건 확인 |
| 다중 자원 명령·생성/삭제 ID | 한 RAD 자원의 원자 생성/할당·구조 변경과 stable UUID/native ID는 구현됐다. N16 복합 명령은 PR20, 첫 N18 절대좌표 이동의 sparse native 행 codec은 PR29에 병합했다. 나머지 다섯 메시 연산은 기존 codec·원자 명령을 재사용해 연결하며 N17 전체 예산은 미완료다 |
| CAD 교체·재메시 후 조건 연결 | CAD 후보의 소유 메시 교체는 참조가 없을 때만 허용하며 공유 절점을 보존한다. N16의 준비된 mesh INCLUDE 교체는 참조를 stale로 보존하고 명시 source/revision 대응으로 재연결하며 미해결이면 출력을 차단한다. 일반 메시 수정·CAD 재메시는 N18 |
| MCP 서버·열린 GUI 연결 | N19 IPC와 N20 MCP는 PR #21의 실제 Linux GUI·공개 client 검사 범위로 구현·병합했다. 독립 CLI와 구분하고 Windows·자연어 LLM 사용은 미확인으로 유지하며 기존 Workbench JobManager 책임 유지 |
